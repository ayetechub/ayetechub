Top 10 PLC Programming Best Practices

📅 April 28, 2026 ✍ Awet G. Nway 🕑 8 min read
🌐 Read in:

A PLC program that works on commissioning day is good. A PLC program that a different engineer can understand, modify, and maintain five years later without calling you — that is professional. The difference between the two is coding discipline.

I have seen industrial programs written without a single comment, with every output addressed as Q0.0 through Q127.7 and no meaningful names anywhere. I have also seen programs so well structured that a maintenance technician with basic PLC knowledge could diagnose a fault in minutes. These 10 practices will move your code firmly into the second category.

The 10 Practices

1

Always Use Symbolic Names — Never Raw Addresses

Never write I0.0 directly in your logic. Always assign a meaningful symbolic name: PB_Motor_Start. When the hardware changes and I0.0 becomes I2.3, you change one entry in the tag table — not every rung that referenced the address. In Siemens TIA Portal, use the PLC tag table. In Allen-Bradley Studio 5000, use controller tags. In both systems, meaningful names are not optional — they are the foundation of maintainable code.

// BAD — unreadable, breaks if I/O mapping changes IF I0.0 AND NOT I0.1 THEN Q0.0 := TRUE; END_IF; // GOOD — self-documenting IF PB_Motor_Start AND NOT E_Stop_Active THEN Motor_Run := TRUE; END_IF;
2

Structure Code in Function Blocks (FB), Not One Giant OB1

Placing all your logic in OB1 is the PLC equivalent of writing an entire application in a single function. Break your program into Function Blocks: FB_Motor_Control, FB_Conveyor, FB_Alarm_Handler. Each FB handles one piece of equipment or one process area. OB1 just calls them in sequence. This makes testing, debugging, and modification dramatically simpler — and it makes your code reusable across projects.

3

Use User-Defined Types (UDT) for Repeating Equipment

If your plant has 12 motors, 12 valves, and 8 pumps, do not create separate variables for each one. Create a Motor_Type UDT with fields for Running, Fault, Speed, RunHours, and StartCount. Then declare an array: Motors : ARRAY[1..12] OF Motor_Type. When you add a field to the UDT, all 12 motors get it automatically. When you write a diagnostic screen, one FB handles all 12. This is how professional automation code scales.

4

Follow a Consistent Naming Convention and Never Change It

Pick a convention before you write a single line of code and document it. A common industrial standard: [Type]_[Location]_[Device]_[Attribute]. Example: DI_Line1_LS_High (Digital Input, Line 1, Level Switch, High). Every engineer who opens your project should be able to read any tag and know exactly what it does, where it is, and what kind of signal it represents — without opening any documentation.

5

Write Comments That Explain WHY, Not WHAT

The code already shows what it does. Comments should explain why a decision was made. // Motor sealed-in contact: holds motor ON after start button released is useful. // This is the motor rung is useless. Comment on: non-obvious interlocks, safety-critical decisions, customer-specific requirements, and workarounds for hardware limitations. Delete comments that simply repeat what the code clearly shows.

6

Always Simulate Before Going Live — Use PLCSIM

Siemens PLCSIM and PLCSIM Advanced simulate the full CPU including PROFINET, OPC-UA, and HMI connections. Allen-Bradley has Logix Designer Offline. There is no excuse for commissioning untested code on live equipment. Develop a simulation test plan: test every input condition, every interlock, every fault scenario. A fault you find in simulation costs 5 minutes. The same fault found on live equipment during production can cost hours of downtime and put people at risk.

7

Implement a Fault and Alarm System From Day One

Every PLC program needs alarm management. Define alarm classes (critical, warning, information), assign each alarm a unique number, and store the alarm history in a data block. In TIA Portal, use the AlarmDB with timestamp, first occurrence, and acknowledgement tracking. An HMI operator should always be able to see the current fault, when it started, and what action to take. Operators who cannot quickly identify faults make dangerous decisions.

8

Version Control Your PLC Programs

Export your TIA Portal project archive (TIA Archive) to a version-controlled folder every time you make significant changes. Label versions clearly: ProjectName_v1.0_Commissioning_2026-05-15. Many engineers have lost weeks of work because a program was overwritten without a backup. For team projects, consider using TIA Portal's built-in multiuser engineering or a Git-based workflow with project file exports. Your PLC program is engineering intellectual property — protect it.

9

Monitor and Optimize Scan Cycle Time

Use the CPU diagnostics in TIA Portal (Online → Cycle Time) to monitor minimum, maximum, and current scan cycle time. If your scan time is approaching the watchdog timer limit (or exceeding your control requirements), identify which OBs are consuming the most time using the program cycle time measurement feature. High-frequency tasks (PID loops, motion control) belong in cyclic interrupt OBs (OB35) running at 5–10ms, not in OB1 which may run at 50–100ms.

10

Design for Maintenance, Not Just Commissioning

The commissioning engineer leaves after 2 weeks. The maintenance technician lives with your code for the next 10 years. Every design decision should consider: Can a technician bypass this valve for maintenance without stopping the whole line? Is there a manual mode for each actuator? Can a fault be acknowledged without restarting the whole system? Are LOTO (Lockout/Tagout) states represented in the program? Programs designed for maintenance save enormous time and prevent accidents.

"The best PLC code is code that a competent engineer who has never seen this project before can understand within 30 minutes of opening it."

Quick Reference Checklist

  • ☑ All I/O uses symbolic names from tag table
  • ☑ Logic structured in FBs with clear purposes
  • ☑ UDTs defined for all repeating equipment
  • ☑ Naming convention documented and followed
  • ☑ Comments explain WHY, not WHAT
  • ☑ Full simulation test completed before live commissioning
  • ☑ Alarm system with history and acknowledgement implemented
  • ☑ Project archive saved with version label before every major change
  • ☑ Scan cycle time measured and within acceptable limits
  • ☑ Manual mode and maintenance bypass available for all key actuators
